# Research report — local render commits

Date: 2026-10-07 UTC

## Target and environment

Test repeated template updates and shared paths in isolated jj repositories.
Then test a local `new` and `update` prototype with optional generated content.
The nested devenv pins jj 0.45.1, Git 2.55.0, and Python 3.13.14. Copier is
absent. The [toolchain record](evidence/2026-10-07/toolchain.txt) and
[full experiment transcript](evidence/2026-10-07/transcript.txt) contain the
run evidence.

Command: `cd .scratch/projects/12-jj-render-merge && devenv test`

Result: 73 spike assertions and 9 prototype tests passed. Ruff passed on the
prototype Python files. The tests used only temporary jj repositories. They
did not change a managed CopyRoom project.

## Findings

The second update used T1 as its merge base. T2 was a child of T1. Project
edits before and after the first update survived the second merge. The local
prototype found the latest marked render ancestor with `heads(::@ &
subject(glob:...))`. The graph supplied the merge base after that lookup.
The graph alone did not name the layer's current render head. The
[jj revset reference](https://docs.jj-vcs.dev/latest/revsets/) defines the
ancestor, `heads`, and subject selection used here.

Two layers cannot safely own one path under the tested graph design. Identical
initial files merged cleanly. A later delete in one layer removed the file
without a conflict, although the other layer still rendered it. Nearby edits
from the project and both layers produced a three-sided conflict. The
[jj conflict guide](https://docs.jj-vcs.dev/latest/conflicts/) confirms that
jj records conflicts in commits and supports merges with several sides. The
silent deletion is a local test finding, not a claim from that guide.

The prototype stores answers and the local template path in a project marker.
It stores no render commit ID. It uses a stable project ID in render commit
descriptions and requires one current render head. An explicit `--generated`
directory supplies generated bytes. The prototype commits those bytes into
the render line before the merge. Later updates reuse them until the operator
supplies a new snapshot.

## Failures and fixes during this run

The first prototype test run failed two cases before jj initialization. The
test answers lacked `project_name`, which the existing fixture uses. The
renderer correctly rejected that undefined answer. The test now supplies all
fixture answers. The focused rerun passed all six tests. Three later tests
confirmed that generated files cannot claim the same path as template files,
including a file-directory prefix, during `new` or `update`. A rejected update
left the active jj commit and project files unchanged. The final `devenv test`
run passed the full suite.

The first overlap hypothesis was that equal initial bytes gave both layers
safe ownership. The deletion test rejected it. The chosen rule is one active
owner per path. A conditional seed in a second template is safe only if that
layer's committed render omits the path on every later update.

## Limits and next boundary

The renderer supports scalar substitutions, UTF-8 template text, and local
files. It is a prototype, not a complete Copier replacement. It does not
implement layers, remote templates, a question schema, or an LLM provider.
An external LLM can write a local generated snapshot; the prototype freezes
that snapshot only when the operator passes `--generated`.

Gitman has no command for creating render lines and merging them into a
managed project. The prototype calls jj directly only inside disposable test
repos. Do not run it in a gitman-managed project. Retire the prototype when
gitman exposes the required graph operations and a production renderer passes
equivalent tests. No upstream jj patch was needed.
